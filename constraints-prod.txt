# AssetAtlas runtime constraints — the VERSION half of the runtime manifest.
#
# requirements-prod.txt states INTENT: which packages the runtime needs, and the
# floors/caps that intent implies. It stays readable and stays hand-edited.
# This file states VERSIONS: the full transitive closure, pinned exactly. Every
# site that installs requirements-prod.txt passes it with `-c` (Dockerfile.base,
# Dockerfile.base.online, the three test jobs in .github/workflows/tests.yml).
#
# WHY (#1262). Of the 52 lines in requirements-prod.txt, 49 declare a `>=` floor
# with no upper bound (two are pinned exactly, and only mcp is capped), so a
# COLD resolve takes whatever is latest that minute. On 2026-07-28 `mcp`
# published 2.0.0, which removed `mcp.server.fastmcp` — a module 22 files
# under src/mcp/ import — and nothing in dev CI went red for three
# releases. It could not: the self-hosted fleet's 8 runners share one persistent
# site-packages, so `pip install -r` reports "Requirement already satisfied" for
# anything whose installed version still clears the floor. The fleet never
# upgrades and therefore never resolves cold. Only two things do — the public
# mirror's ephemeral runners, and a base-image rebuild — and the second one is
# the one that ships. Production survived on luck: release.yml's deps-fingerprint
# guard kept reusing the previously-built base by digest, so the broken resolve
# was never baked. #1261 capped `mcp` specifically; this file removes the class.
#
# HOW IT WAS SEEDED. Not from a fresh resolve — from `pip list` inside the
# published base image (ghcr.io/dotdna-io/assetatlas-base, deps-sha 4bdd2d3f…),
# i.e. the exact package set every current deployment is running. Adopting
# today's latest for 50 uncapped packages would have swapped a proven dependency
# set for one nobody has run, under cover of a change advertised as "pinning".
# These pins are content-neutral by construction: rebuilding the base against
# them produces the image that is already deployed.
#
# torch is absent on purpose and must stay absent. It is not in
# requirements-prod.txt, not installed by Dockerfile.base (ONNX Runtime replaced
# it in #1070), and not in the published base. A plain `pip install torch`
# resolves the CUDA build on linux/amd64 and drags in ~2.8 GB of nvidia-* wheels.
#
# REGENERATING. uv 0.12+; targets the platform Dockerfile.base builds for.
#
#   # re-resolve after editing requirements-prod.txt, keeping existing pins:
#   uv pip compile requirements-prod.txt \
#     --python-version 3.13 --python-platform x86_64-manylinux_2_28 \
#     --no-header --no-annotate -o constraints-prod.txt
#
#   # bump one package (or --upgrade for all — read the diff before committing):
#   uv pip compile requirements-prod.txt --upgrade-package <name> … -o constraints-prod.txt
#
# Then re-add this header: `uv pip compile` writes the body only.
#

# until scripts/publish-base-image.sh is re-run. That is the point: a pin the
# base can drift away from is not a pin.
